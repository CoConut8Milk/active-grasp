# 06 常见问题排查

按症状查表。原则：**先确认现象，再看日志，一次只改一个变量**。

## 环境层

| 症状 | 原因与处理 |
|---|---|
| `setup_wsl2.sh` 下载很慢 | 换 apt 镜像源（清华/阿里），重跑 |
| pip 装 numpy 报错 | 网络问题；用 `-i https://mirrors.aliyun.com/pypi/simple/` |
| `rosdep init/update` 报 GitHub raw 连接失败 | 网络拦截了 `raw.githubusercontent.com`（与 WSL 安装超时同一原因）。rosdep 只是辅助工具，**不影响本项目编译运行**；最新版 `setup_wsl2.sh` 会自动改用中科大镜像重试 |
| 跑脚本报 `AMENT_TRACE_SETUP_FILES: unbound variable` | ROS Humble 的 `setup.bash` 与脚本里 `set -u` 的已知冲突；已修复（source 前临时关闭 nounset），`git pull` 后重试即可 |
| 运行 launch 报 `'NotImplementedType' object is not iterable` | launch 条件写法不兼容 Humble（已修复 `sim.launch.py`），`git pull` 后重试即可 |
| Gazebo 打开后没有桌子/回收盒，机器人摔在地上 | `ag_gazebo` 的 world 文件没被安装进 `share`（已修复 `setup.py`）；`git pull` 后重新 `bash scripts/build.sh` 再跑 |
| 机械臂瘫倒、spawner 一直等 `/controller_manager` | Gazebo Classic 下 controller_manager 由 `libgazebo_ros2_control` 插件内建，不能再单独启动 `ros2_control_node`（已修复）；`git pull` 后重新 build 再跑 |
| 节点启动即崩溃（execution_node / perception_node） | 参数文件里用了 ROS 2 不支持的嵌套列表/字典，且 `use_sim_time` 被重复声明（均已修复）；`git pull` 后重新 build 再跑 |
| 插件报 `Couldn't parse parameter override rule` | URDF 里的 XML 注释/换行会破坏插件注入参数（已修复：launch 自动剔除注释并压成单行，与 xacro 输出对齐）；`git pull` 后重跑 |
| `demo`/`train` 报 `unrecognized arguments: --ros-args` | Python argparse 与 launch 附加的 ROS 参数冲突（已修复）；`git pull` 后重跑 |
| 夹爪不动：`Skipping joint in the URDF named 'finger_left'` + `Failed to activate controller : gripper_controller` | Gazebo Classic 默认把固定关节"合并"进父连杆，`tool0` 无惯性质量时连挂在它下面的两根手指关节一起被删掉。已修复：给 `tool0` 加惯性 + 对 `tool0_joint`/`camera_joint` 设 `preserveFixedJoint`；`git pull` 后重新 build 再跑 |
| `perception never produced a state` / `not calibrated yet: ...` | 感知节点要先等到深度图 + 机械臂静止（发射后先回 home 位）才开始标定。已修复：等待上限放宽到 120 s，并会每 3 s 打印一条 `not calibrated yet: <原因>`，照着原因排查即可 |
| `not calibrated yet: robot still moving (joint '...' position delta = 0.09)` | 机械臂到位后在缓慢下沉漂移：Gazebo 的位置命令接口是 P 控制器，默认增益 0.1 太小。已修复：URDF 里给插件加 `position_proportional_gain=10`，感知的静止阈值放到 0.15（Gazebo 在 WSL 下会残留 0.05~0.1 的速度噪声）。若仍报，请把这行发出来——它会告诉你是哪一个关节 |
| `TimeoutError: service /world_manager/reset_scene timed out`（demo 启动即退出） | 重置场景的删/建实体调用是在服务回调里阻塞执行的，Gazebo 还在加载机械臂时会很慢。已修复：世界管理器改用专门的辅助节点做阻塞调用、等 `/spawn_entity` 就绪、逐条打印 `spawned ag_obj_x`，demo 侧超时放宽到 120 s 并自动重试一次 |
| 抓取/推动服务调用超时 | 一条抓取计划包含多段轨迹，WSL 里仿真慢于实时（RTF≈0.3）会导致墙钟时间是仿真时间的 3 倍。已修复：`grasp/push/move_view` 超时放宽到 180 s，轨迹等待用 `spin_once` 轮询，保证回调里也能收到 action 结果 |
| demo 能跑但总抓空、高度图像左右镜像 | 水平镜像**无法**从一张水平桌面的深度图里分辨（镜像后的桌面照样是平的：实测两种取号的方差都恰好为 0），旧代码用"平面最平"自动选号，实机上等于掷硬币。已修复：`u_sign/v_sign` 按相机约定固定为 -1（竖直方向仍由启动标定实测，用来发现相机倒装），日志会打印 `camera signs: ... (flat-plane estimate ..., u unobservable)`；新增单元测试 `test_flat_table_cannot_observe_horizontal_sign` 记录这件事 |
| Gazebo 闪退 / 黑屏 | WSL2 显示问题：Windows 11 用 WSLg；Windows 10 装 VcXsrv 并 `export DISPLAY=$(cat /etc/resolv.conf \| grep nameserver \| awk '{print $2}'):0` |
| 编译缺 `rosidl_default_generators` | 确认 source 了 `/opt/ros/humble/setup.bash` 再 colcon |
| OneDrive 目录里编译巨慢 | 把项目复制到 `~/ros2_ws/src`（9P 文件系统性能差） |

| `ValueError: x0 is infeasible`（execution_node 直接崩溃） | scipy 不接受越界的 IK 初值：关节停在限位上或状态里出现 NaN 时 `least_squares` 会抛异常。已修复：IK 先把种子裁剪到限位内部并清洗 NaN、`ik_retry` 单个种子失败不再中断、执行节点拒绝非有限轨迹并把轨迹裁剪进限位、四个服务回调都加了兜底，异常只会让当前动作失败而不会杀死节点 |
| `recovery: home move failed` / `trajectory did not reach` | 控制器返回非零 error_code 而机械臂其实已经到位。已修复：先按 `/joint_states` 核对（关节误差 <0.05 rad 视为成功）并打印真实 error_code；同时把物体生成范围收窄到 IK 验证过的可达区域（`spawn_margin` 0.035→0.06），减少"高度图指向够不到的位置"这类无效尝试 |
| 每次都去抓**同一个角落格子**、然后报 `trajectory did not reach` / `IK found no solution` | 深度图最外圈像素是噪声，被当成"永久存在的高点"（坐标固定 x≈0.205、y≈0.245，每个 episode 都一样，所以一定够不到）。已修复：感知丢弃最外圈 3 像素（`valid_border`），动作掩码也排除最外圈 3 格（`ActionSpace(..., border=3)`）；移动失败时现在会打印具体原因（控制器拒收 / 请求超时 / error_code）。新增单元测试 `test_valid_mask_excludes_unreliable_border` |

| `State tolerances failed for joint 4: Position Error: -6.283174` + `Aborted due to goal_time_tolerance` | IK 返回了 ±π 的另一侧分支：±π 在姿态上完全等价，但在关节空间差整整一圈，控制器于是真去转 6.28 rad，然后超时中止。已修复：下发轨迹前把每个关节平移到离当前位置最近的等价角度（`nearest_joint_branch`，只做 2π 整数倍平移，末端姿态不变）；同时把"等待控制器接受目标"的上限放宽到 30 s（控制器忙时以前会误判为无响应）。新增单元测试 `test_nearest_joint_branch_avoids_full_turn` |

| 每个动作都报 `arm controller did not answer the goal request`，但控制器日志明明显示 `Received/Accepted/Goal reached` | 执行节点在**自己的服务回调里**手动 `spin_once` 等 action 结果，第二次之后就不再处理回调，于是目标其实发出去了、客户端却收不到回执。已修复：`main()` 改用 `MultiThreadedExecutor(3)`，四个服务放进独立回调组，阻塞等待只 `sleep` 轮询，由执行器其它线程送结果；启动动作移到 `startup()`（执行器已在转）里做 |
| 机械臂动作正常但**什么都抓不起来** / Gazebo 里看不清爪子 | 两个原因：(1) 旧抓取计划用固定 `grasp_offset`，指尖每次都只比物体顶部低 5 mm，只掐住顶边必然滑掉；(2) 手指只有 1.6×2 cm 且被相机盒子挡住。已修复：下降深度按 `tool_z = max(0.01, 0.5·z_top) + finger_length(0.07)` 计算，指尖落在物体半高处；手指加粗到 2×2.6×6 cm、指间仍为 4 cm，并改用深色材质（`Gazebo/DarkGrey`）；物体随机尺寸限制在 4 cm 以内以适配夹爪开度 |

| `gzserver ... process has died [exit code 255]` + `Controller already loaded, skipping load_controller` + `Failed to configure controller`，随后手臂几乎不动、TF 误差几百毫米 | 上一次仿真没退干净，旧 gzserver 还占着端口/控制器管理器。新 Gazebo 直接退出，控制器、传感器却连到了旧实例上，所以"看起来在跑"其实完全失效。处理：`pkill -f gzserver; pkill -f gzclient` 后再启动；`run_demo.sh` 现在会在启动前检测旧 gzserver 并提示；`execution_node.startup()` 也会核对机械臂真的到达 home（关节误差 >0.1 rad 直接报错），不会再假 ready |
| 高度图里出现 `z=0.350` 的"物体"、demo 去抓一个 34 cm 高的东西 | 机械臂自身连杆进入了相机视野，而 `z_max` 之前是 0.35。已修复：感知的 `z_max` 收到 0.12（物体 ≤4.5 cm、边界墙 6 cm），手臂连杆不会再被当成目标 |

| 抓取点精确（`tool pose ... error=0.0 mm`）、夹爪完全闭合（`width_at_hold` = 全闭间隙）、物体几乎不动（`heightmap delta≈0`） | **夹爪装反了**：手指沿 -tool z 伸出，而旧的抓取姿态把 tool z 朝下，指垫落在法兰上方 0.086~0.146 m，根本到不了桌面。已修复：`grasp_orientation()` 改为单位阵（tool z 朝上、手指朝下），`push_orientation()` 同样保持 z 朝上；新增回归测试确认指尖在法兰下方、贴近桌面 |

| `spawn_entity ... Service /spawn_entity unavailable` + `Spawn service failed. Exiting.`，随后相机没数据、demo 报 `perception never produced a state` | gzserver 在 WSL 里冷启动太慢（这次约 30 s），`spawn_entity` 的 30 s 超时先到了，机械臂没生成。已修复：`sim.launch.py` 的 `-timeout` 改为 180 s；世界管理器也会等 `/spawn_entity` 最多 90 s |

| 碰到物体后整台机械臂翻倒 / 关节误差突然涨到 2 rad，`Position Error 0.37` | 机器人底座没有固定，只是一个 2 kg 的自由刚体；机械臂伸出 1 m 后一接触物体，反作用力就把整台机器推下桌子。已修复：底座加宽到 24 cm、质量 20 kg，并对 `base_link` 设 `kinematic=true`（基座钉在世界里，关节照常运动） |
| 下降阶段把物体撞飞（`heightmap delta` 7~11 cm，且 `width_at_hold` 仍等于全闭间隙） | 夹爪开口余量不足：物体约 3.4 cm，原来开口 5.6 cm，每侧只有 1.1 cm，高度图格子量化误差就足以让指面扫到物体边缘。已修复：开口加大到 7.0 cm（每侧 1.8 cm 余量），全闭 0.2 cm |

| gazebo 里夹爪看起来只是几块橙色方块、不像夹爪 | 旧模型只有两根悬空的指垫，没有掌部，视角一变就只剩方块。已重写：`gripper_base`（11×6×2 cm 掌部，深灰）+ 两根橙色长指（7.5 cm），指尖在 tool0 下方 10.5 cm；固定关节已 `preserveFixedJoint`，避免被 Gazebo 合并掉 |
| `jaw contact` 在第一步就触发、`width` 还很大 | gazebo 位置环是慢速一阶响应：0.3 s 的步进根本来不及走完，用"宽度变化量"判断必然误判。已改为：先开爪并等宽度稳定（`_wait_gripper_stable`），再用 4 个大步进、每步 0.9 s，按"实际移动 < 25% 期望"判定被挡住 |

| `Position Error` 在同一个 goal 里同时出现在 joint 0~5（0.1~3.0 rad），随后 `Aborted due to goal_time_tolerance` | IK 在相邻轨迹点之间换了构型分支（肘上↔肘下），关节一次要转 1~3 rad，慢位置环跟不上。已修复：①URDF 收紧 joint2/joint3/joint4/joint5 限位；②IK 加姿态正则，解保持在当前构型附近；③`max_joint_speed=0.6 rad/s`，大跳变自动拉长轨迹时长；④物体只在已验证可达的 x∈[0.40,0.62]、y∈±0.12 内生成 |

| `tool pose ... actual (-0.51, …) error=1010 mm`、`stretching move ... 3.14 rad` | IK 返回了"整机转身 180°"的镜像解（joint1≈π），机械臂绕到桌子背面后撞到桌子，末端离目标 1 m。已修复：`ik_retry` 不再返回第一个收敛解，而是收集所有候选并选"离当前构型最近"的那个；demo 的质心吸附结果也会被夹在可执行边框内（之前会吸附到 u=1 的角格） |

## 启动层

| 症状 | 处理 |
|---|---|
| 没有 Gazebo 窗口 | 看终端报错；`gui:=true` 是否被覆盖；确认 Gazebo 可单独启动（`gazebo`） |
| 机械臂不出现 | `spawn_entity.py` 超时：确认 robot_state_publisher 在跑、`/robot_description` 有话题 |
| `arm_controller` 不存在 | `ros2 control list_controllers` 看状态；controller_manager 日志 |
| 一直不打印 `perception ready` | 机械臂没到 home 或相机没数据：`ros2 topic hz /ag_camera/depth/image_raw` |
| 一直打印 `observe called before calibration` | 相机标定没完成；查 TF：`ros2 run tf2_ros tf2_echo base_link camera_link` |

## 相机与感知层

| 症状 | 处理 |
|---|---|
| 深度话题不存在 | `ros2 topic list \| grep ag_camera`；确认话题名与 perception.yaml 一致 |
| 深度全 0 或 NaN | 相机 min_depth/max_depth；物体是否在 0.05–2.0 m 内 |
| 标定出的镜像符号反了 | 高度图左右/上下颠倒：检查 `auto_calibrate` 日志打印的 signs，必要时在配置里固定 |
| 高度图大面积空洞 | 相机看不到桌面（默认视角太低/太远）；调 `execution.yaml` 的 `home_camera_pos/look` |

## 运动与抓取层

| 症状 | 处理 |
|---|---|
| IK 频繁失败 | 目标超出可达空间；换更近的位姿；增大 `seed_sets_flat` |
| 机械臂与桌子碰撞 | 运动原语路径不够安全：提高 `approach_offset` / `lift_height` |
| 抓不住物体 | 增加手指摩擦（URDF 里 `mu1/mu2`）、减小物体质量、降低闭爪速度 |
| 抓住后掉落 | 提升 `lift_height`、缩短搬运距离；检查回收盒边缘高度 |
| 服务返回 `success: false` | 看 execution_node 的 warn 日志，通常是 IK 或轨迹执行失败 |

## 训练层

| 症状 | 处理 |
|---|---|
| 每回合都超时且清理率恒 0 | 抓取成功率太低：先跑 demo 确认单次抓取可靠，再训练 |
| 奖励震荡不收敛 | 减小 lr（1e-4）、增大 replay 容量、调大 gamma 到 0.95 |
| 从不使用视角动作 | 视角奖励太小：增大 `env.py` 的 2.0 系数；或减小视角时间成本 |
| 视角用得太频繁 | 反之调小视角奖励、增大成本 |
| CPU 训练太慢 | 减小 `grid_width/height`（32×32）、减小网络 base_channels |
| 显存/内存不足 | 减小 batch_size 与 capacity |

## 通用调试三件套

```bash
ros2 topic list                      # 有哪些话题
ros2 topic hz /ag_camera/depth/image_raw   # 相机是否在发数据
ros2 service list                    # 服务是否注册
ros2 run tf2_ros tf2_echo base_link camera_link   # TF 是否连通
```

## 还没有解决？

把终端完整报错和上面三件套的输出一起发给导师/讨论区。**不要只贴最后一行**——
排查问题需要完整日志。
